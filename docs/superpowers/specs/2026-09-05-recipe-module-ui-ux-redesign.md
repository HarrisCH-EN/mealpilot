# 菜谱模块 UI/UX 重构设计

## 目标与范围

在原生微信小程序技术栈中重构菜谱总览、菜品详情和菜谱编辑三个页面。视觉以用户提供的方案 B 效果图为基准，采用低饱和粉白云雾背景、暖白半透明卡片、克制粉色强调、弱阴影和充足留白。业务行为继续使用现有 API，不修改数据库 Schema、后端接口或菜单页。

## 已确认的数据边界

- 菜谱只存在 `cover_url` 单封面字段；创建和更新接口不接受封面，项目也没有上传接口。编辑页只展示当前真实封面，不提供虚假的多图数量、上传按钮或不可工作的图片管理。
- 食材没有图片字段。界面使用统一的文字首字占位，不伪造食材图片数据。
- 制作步骤由单个 `TEXT` 字段保存。前端将非空换行解析为独立步骤块，支持新增、编辑、删除和上下排序，保存时再合并成换行文本。
- 收藏不进入服务端。收藏菜谱 ID 保存在小程序本地 storage，并在界面明确标注为本机收藏、不跨设备同步。
- 服务端搜索目前只支持菜名，搜索框继续使用“搜索菜名”，不暗示尚不存在的食材或菜系联表搜索。
- 服务端分类只接受荤菜、素菜、汤、主食；分类栏只展示全部与这四个真实分类。

## 共享视觉系统

创建 `miniprogram/styles/recipe-theme.wxss`，只由三个菜谱页面导入。`.recipe-cloud-page` 作用域内声明菜谱模块 token，包括主题粉、柔粉、暖白表面、正文与辅助文字、层级圆角、柔和阴影和统一间距。页面背景由多个极浅 radial-gradient 与暖白底色叠加；公共 `app.wxss` 不改动，避免影响菜单页。

## 菜谱总览

页面占满可用视口并禁止整页滚动。标题和搜索固定在顶部；主体为横向 flex，左侧分类 `scroll-view` 和右侧菜谱 `scroll-view` 各自滚动。右侧使用两列网格卡片，图片保持 1:1、菜名最多两行、元数据单行截断。卡片收藏按钮写入本地 storage，加入菜单按钮继续打开真实菜单底部面板。删除入口移入详情页更多菜单，避免列表出现后台式红色删除文字。

loading、empty 和 error 状态只占右侧内容区，不改变分类栏和页面整体尺寸。图片加载失败后清空该条 `coverUrl`，显示统一暖白餐盘占位。

## 菜品详情

页面使用自定义导航：左侧返回，右侧本机收藏和更多；更多菜单提供真实编辑和删除操作。Hero 使用外层暖白陶瓷盘壳、中层米白环和内层圆形图片形成明显但克制的盘子效果，图片失败后显示菜名字首占位。

标题和副标题居中；难度、烹饪时间、人数组成三列轻量信息单元。食材与步骤分别放入暖白大卡片，食材行使用统一占位头像，步骤使用两位粉色序号。底部加入菜单按钮固定在安全区上方，正文增加相应底部 padding。

## 菜谱编辑

页面使用自定义导航，保存按钮是唯一保存入口。首段封面区域只展示现有单封面和真实能力说明。基础信息放入一张卡片，用分组和浅底输入区形成消费级编辑体验。

食材卡片展示紧凑行，点击行或“添加食材”打开底部面板；面板编辑食材选择、克数和备注，确认后更新前端数组。删除使用弱粉圆形减号并阻止触发行编辑。重复食材在确认时被拦截，避免触发数据库唯一约束。

步骤卡片由稳定 `key` 标识的步骤对象组成。每块包含序号、文本输入、上移、下移和删除；添加步骤生成新的稳定 key。加载时从 `TEXT` 解析，保存时过滤空白并重新序列化为换行文本。

## 状态与错误处理

- server state：菜谱、食材选项和保存请求结果。
- UI state：底部面板、收藏状态、步骤 key、加载与提交状态。
- 所有可见按钮均绑定真实事件；无服务端能力的图片上传入口不渲染。
- 请求错误提供重试或明确 toast/modal；保存时防重复提交。
- fixed 区域使用 `env(safe-area-inset-bottom)`，自定义导航根据系统状态栏和胶囊位置计算高度。

## 验证

使用 Node 内置测试验证步骤 parse/serialize、本地收藏帮助函数、WXML 事件绑定、双独立滚动、两列网格、陶瓷盘层级、编辑底部面板、稳定 `wx:key`、safe area、图片 fallback，以及未修改菜单页契约。运行完整前端和后端测试，并在微信开发者工具中编译、检查控制台、按核心路径进行交互和视觉对照。
