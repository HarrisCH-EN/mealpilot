# 菜单上下文与推荐可靠性设计

## 目标

修复菜谱、菜单和推荐页面之间的状态断裂：用户从某天某餐次开始的操作必须保留该上下文；同一道菜不能在未告知的情况下覆盖备注；一组推荐必须以单一事务应用到菜单；不可用的偏好不得伪装为已生效。

## 菜单上下文

新增一个仅在小程序运行期保存的菜单上下文模块。上下文为 `action`、`menuDate`、`mealType` 和可选 `menuItemId`：

- 菜单页进入菜谱 Tab 时保存 `action: 'add'`；菜谱页只在用户点击一张菜谱的“加入菜单”按钮时消费它。
- 顶部加菜默认当前激活餐次；空餐次加菜使用该卡片的餐次。
- 菜单菜品进入详情页时通过页面参数传入日期、餐次与菜单项 ID。详情页显示“已加入 [日期][餐次]”，主操作改为“查看菜单”。
- 从详情页查看菜单时保存 `action: 'focus'`，菜单页在 `onShow` 消费它，定位对应日期和餐次。

上下文消费后立即清除。用户直接进入菜谱页、直接进入详情页时仍使用“今天、晚餐”的明确默认值。

## 加菜状态

`POST /menus/items` 不再用重复请求覆盖已有备注。若同一菜单已包含同一菜谱，接口返回 `status: 'already-present'`、菜单项 ID 和现有备注；新建时返回 `status: 'created'`。菜谱页和详情页据此展示“已加入当前菜单”，而不是“已加入菜单”的泛化提示。详情页从菜单进入时不再显示加入表单。

## 推荐原子采纳

生成推荐时创建一条 `recommendation_runs` 和多条 `recommendation_items`，响应带回 `runId`。新增 `POST /recommendations/:id/apply`：它在一个数据库事务中验证家庭归属、读取推荐菜品、创建或取得目标菜单、插入缺失的菜单项，并把菜单关联到该推荐批次。重复采纳保持幂等，不改写手动添加的备注。前端只调用该接口，成功页展示新增数和已存在数；失败页不会暗示一部分菜已被安排。

## 会话与偏好承诺

推荐页只在没有会话令牌时执行演示登录；已有会话用 `/auth/me` 进行验证。口味与饮食限制在本次请求不发送时，编辑区明确写为“保存为本机草稿，暂不影响推荐”，并移除误导性“已为你推荐更符合口味”等文案。

## 验收

1. 在任意历史日期打开午餐空餐次并加菜，面板预置该日期和午餐。
2. 从菜单菜品进入详情，能看见已加入状态并可返回对应菜单；不出现重复加入主按钮。
3. 对同一日期、餐次、菜谱重复确认，不会覆盖备注；用户收到已存在状态。
4. 推荐采纳只产生一次原子事务；模拟失败时没有部分菜单写入。
5. 已有登录会话进入推荐页不会被切换为演示用户。
6. 偏好编辑区不再承诺未接入的筛选效果。
