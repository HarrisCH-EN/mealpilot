# 推荐系统设计说明

更新时间：2026-09-18（Asia/Shanghai）

## 1. 目标与输入

推荐接口根据家庭成员身份、目标日期、餐次、标签偏好、准备时间、菜品数量和菜品结构生成可解释候选。家庭忌口是硬约束；成员类别偏好、季节、营养和新颖度进入软评分。

## 2. 处理流水线

```text
校验请求与家庭成员
  → 读取家庭菜谱、标签、偏好、忌口和近期菜单
  → 过滤硬性忌口与不可用菜谱
  → 按结构槽位生成组合（荤菜 / 素菜 / 汤 / 主食）
  → 计算准备时间、营养、季节、重复度和多样性
  → 加权排序并保留最多 3 个候选
  → recommendation_runs / candidates / candidate_items 持久化
  → 返回候选与解释文本
```

## 3. 规则与评分

当前权重总计 100：

| 因子 | 权重 | 含义 |
| --- | ---: | --- |
| preference | 30 | 家庭成员类别偏好匹配 |
| ingredientDiversity | 15 | 食材重复控制 |
| methodDiversity | 10 | 烹饪方式重复控制 |
| nutrition | 15 | 结构与营养覆盖 |
| seasonal | 10 | 季节食材匹配 |
| novelty | 20 | 相对近期菜单的新颖度 |

忌口先于评分执行；命中成员限制的菜谱不会通过硬过滤。准备时间以组合中最长烹饪时间为基础，对剩余准备工作按半量向上取整；候选优先落在目标准备时间内，必要时才允许超时 fallback。

## 4. 结构约束

结构由请求槽位映射到菜谱类别：荤菜、素菜、汤、主食。每个槽位必须有符合状态、家庭边界和限制条件的菜谱；结构不完整时返回可解释错误，不静默写入半成品菜单。

## 5. 候选持久化与接口

- `POST /api/recommendations` 创建一次推荐运行和最多 3 个候选。
- `GET /api/recommendations/:id/candidates/:rank` 获取指定候选。
- `POST /api/recommendations/:id/apply` 应用候选；新客户端必须提交 `candidateId`。

应用流程在事务中重新读取候选和成员关系，验证候选仍为可用状态、菜谱未被软删除、限制未变化、结构仍满足要求，然后幂等创建菜单和菜单项。重复提交不能产生重复菜单项。

## 6. 兼容与失败处理

旧的无请求体应用接口保留兼容逻辑，但新前端不得依赖它。候选不存在、状态过期、家庭切换、忌口变化和结构不可满足都返回明确错误。服务端不会相信前端传来的评分、理由或家庭归属。

## 7. 可观测性与后续

推荐运行、候选和应用结果应保留可追溯 ID，便于反馈和问题定位。当前系统没有离线模型训练、A/B 实验或长期个性化学习；后续若增加这些能力，必须先定义离线评估集、家庭隐私边界和回滚策略。
